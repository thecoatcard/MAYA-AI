# Phase 09 — Specialist AI Agents

## A. Phase Overview

- **Phase Number:** Phase 09
- **Phase Name:** Specialist AI Agents
- **Objective:** Implement the specialized domain agents as modular, independently testable Python services adhering to strict tool allowlists, model alias bindings, typed input/output Pydantic contracts, and permission ceilings: Research Agent, Coding Agent (integrated with Sandbox Runner), Document Agent, Email & Comms Agent, and the read-only Project Management (PM) Agent.
- **Why This Phase is Necessary:** As established in [`MAYA_AI_FINAL_PLAN.md`](../../../MAYA_AI_FINAL_PLAN.md) §8, monolithic or generic LLM prompts lack the structural rigor and safety constraints needed for production reliability. Breaking capabilities into dedicated specialist agents with scoped tool allowlists, discrete model routing, and deterministic output verification guarantees that agents cannot exceed their operational boundaries.
- **Expected Outcome:** Fully operational and tested specialist agents in `backend/app/agents/specialized/`:
  - `ResearchAgent` (`research` / `heavy` alias; Brave Search; READ ceiling).
  - `CodingAgent` (`heavy` alias; Git, GitHub, Sandbox Runner; WRITE in sandbox, APPROVAL for PRs).
  - `DocumentAgent` (`orchestrator` alias; document generators; WRITE in `/artifacts`).
  - `EmailAgent` (`lite` + `orchestrator`; Gmail adapter; READ + draft WRITE, send APPROVAL).
  - `PMAgent` (`orchestrator`; Notion and Calendar read-only; READ ceiling).
- **Priority:** High
- **Estimated Complexity:** High
- **Estimated Duration:** 15 business days.

## C. Scope

### Included Features

- Research Agent:
  - Model alias: `research` with fallback to `heavy`.
  - Tool allowlist: `brave_search`, `fetch_web_page`.
  - Permission ceiling: READ.
  - Output: Synthesized findings, structured tables, and verbatim citations.
- Coding Agent:
  - Model alias: `heavy` (`gemini-4-argon`).
  - Tool allowlist: `git_status`, `git_diff`, `git_checkout`, `git_commit`, `github_get_issue`, `github_create_branch`, `github_create_pull_request`, `sandbox_run_command`.
  - Permission ceiling: WRITE in local branch/sandbox; push/PR creation is APPROVAL_REQUIRED.
  - Sandbox Runner integration (Decision D14): fixed-function runner, image allowlist, non-root, no host Docker socket.
  - Enables Workflow 3: Issue analysis -> root cause repro in sandbox -> code fix -> test run -> PR submission.
- Document Agent:
  - Model alias: `orchestrator` (`gemini-3.8-flash`) with `lite` for bulk extraction.
  - Tool allowlist: Document engine bindings (`xlsx_engine`, `docx_engine`, `pptx_engine`, `pdf_engine`).
  - Permission ceiling: WRITE restricted strictly to `/artifacts`.
- Email & Comms Agent:
  - Model alias: `lite` for message triage + `orchestrator` for drafting.
  - Tool allowlist: `gmail_search`, `gmail_read_thread`, `gmail_create_draft`, `gmail_send`.
  - Permission ceiling: READ; draft creation = WRITE; email transmission = APPROVAL_REQUIRED.
- Project Management (PM) Agent:
  - Model alias: `orchestrator`.
  - Tool allowlist: `notion_get_page`, `notion_query_database`, `calendar_list_events`, `calendar_get_event`.
  - Permission ceiling: READ (MVP strictly read-only; writes are post-MVP).
  - Enables Workflow 1: Daily briefing & agenda aggregation.

### Excluded Features

- Browser Automation Agent (Playwright) — deferred to Phase 13.
- File Management Agent (arbitrary OS filesystem operations) — deferred to post-MVP.
- Swarm self-cloning or multi-agent debate protocols (post-MVP).

### Deferred Features

- Write-capable PM integrations for Jira, Linear, and Notion page creation (post-MVP).

### Dependencies on Future Phases

- Phase 10 (File Processing) provides the low-level rendering libraries called by the Document Agent.
- Phase 14 (Frontend Experience) renders the specific deliverables and approval cards generated by these agents.

## F. API and Data Contracts

### 1. Specialist Agent Output Contract

```python
class SpecialistAgentResult(BaseModel):
    subtask_id: str
    status: Literal["completed", "failed", "awaiting_approval"]
    summary: str
    data: dict[str, Any]
    artifacts: list[dict[str, Any]] = []
    verification_proof: dict[str, Any]
    approval_request_id: UUID | None = None
```

```python
class SandboxCommandRequest(BaseModel):
    command: list[str]
    working_directory: str = "/workspace"
    timeout_seconds: int = 60
    environment_variables: dict[str, str] = {}
```

## G. Security Requirements

- **Tool Allowlist Isolation:** Agents cannot invoke tools outside their defined allowlists; attempts to bypass restrictions raise security exceptions.
- **Sandbox Hardening:** No root access, no Docker socket mounts, memory capped at 2 GB, execution time capped at 60s, default-deny outbound internet access.
- **Untrusted Output Wrapping:** External text processed by Research and Email agents must be wrapped in `<<<UNTRUSTED_EXTERNAL_INPUT>>>` tags.
- **Irreversible Action Gating:** `gmail_send` and `github_create_pull_request` require verified approval tokens before transmission.

## H. Testing Strategy

- **Workflow 1 Test (Daily Briefing):** Simulate calendar and Notion read requests; assert clean aggregation and markdown output without errors.
- **Workflow 3 Test (Coding Agent Fix):** Seed a test repository with a broken test in sandbox; verify Coding Agent identifies root cause, creates patch, runs sandbox tests to green, and pauses before PR creation.
- **Tool Allowlist Boundary Tests:** Attempt to dispatch a `gmail_send` tool call from the Research Agent; assert failure at the agent boundary.
